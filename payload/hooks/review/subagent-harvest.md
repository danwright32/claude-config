# Subagent issue harvest: how it works and what not to break

Moved out of `~/.claude/CLAUDE.md` on 2026-09-17, word for word, because it was 11,800 characters
loaded into every session and is only needed when changing the harvest, the spool or the issue
review. CLAUDE.md keeps a short pointer here. Read this whole file before editing
`hooks/subagent-issue-harvest.sh`, `hooks/lib/issue-spool.sh`, `subagent-digest.py` or the review hooks.

**Subagent findings are harvested, not remembered.** The issue review above is a `Stop` hook: it fires when the MAIN session stops, on a 30 minute per project cooldown, reading the main transcript. None of that reaches a subagent, so before 2026-08-16 every observation an agent made while working died with it, and a batch of parallel agents got at most one review between them. `hooks/subagent-issue-harvest.sh` is a `SubagentStop` hook that reads the finishing agent's own transcript and spools anything it noticed but was not sent to fix. It asks the agent for nothing, because an instruction to report findings is a rule living only in a prompt (L27) and reaches nothing in exactly the batches where it matters. It runs `async`, so it never delays an agent, and it runs a cheap headless Haiku pass with the global CLAUDE.md and lessons index switched off, since it reads no rule (64,868 input tokens a harvest with them, 29,663 without, claude-config#538), so it costs one small call per agent. Five things to know before changing it. **The transcript to read is `agent_transcript_path`, never `transcript_path`.** A SubagentStop payload carries both, and `transcript_path` is the transcript of the session that SPAWNED the agent. The first version read that one, which does not fail: it harvests the parent conversation and spools findings that look entirely real, and it was caught only by reading the spool file by hand (2026-08-16, three records, every one of them about the parent session). There is deliberately NO fallback to `transcript_path` in any of the three ways it can arrive wrong (absent, equal to the parent, or naming a file that is not there); each is a loud error record instead, and each error names its own cause, because the same-file guard will otherwise answer for the missing-field guard and a reintroduced fallback passes the suite (seen to survive, then caught). The spool lives at `~/.claude-issue-spool/`, deliberately OUTSIDE `~/.claude`, because anything under `~/.claude` auto pushes to the other Mac within seconds and transcript derived notes are not config. Every record also carries the PROJECT key it belongs to, resolved when the record is written (claude-config#294), because attribution used to re-resolve a record's `cwd` later and an agent's cwd is routinely a git worktree that every AGENTS.md says to remove once its PR merges: once it is gone the resolution hashes a path that is not there and the record belongs to nobody. Measured 2026-09-03, 111 of 170 pending records were written from a worktree cwd, and one file held 106 findings nothing could reach. The stamp cannot help a record written before it shipped (L223), so a reader still resolves `cwd` too, and a worktree path also resolves through the checkout it belongs to. It is keyed on the directory of the PARENT SESSION's transcript, which both the harvest and the review derive from the same conversation, so the writer and the reader cannot compute different keys (L70); git's common dir is the fallback for a caller with no transcript (a direct `note`, a test), and a reader also consults that key so nothing spooled the old way is stranded. Keying each side on its own working directory is what let the two drift apart, and 47 findings sat unread for a week because of it. An agent that found NOTHING still leaves a record saying it looked, and an agent whose harvest FAILED leaves a differently worded one, because otherwise both read as a project with no findings (L98, L11). And reading the spool does not empty it: only a `clear` does, run after the picker is answered, so a review that is read and then interrupted leaves the findings behind for the next one. **The review WRITES that clear command into the findings file** (claude-config#287, claude-config#284), on a line reading `TO FILE THESE`, and that line is to be run exactly as it stands. It is not a convenience: a clear takes a directory AND the session transcript, and one given only a directory keys on the git common dir while the render keyed on the transcript's directory. The documented fixed form passed no transcript, so on 2026-09-03 a findings file naming `bfea61f932c1.jsonl (107 records)` was followed by a clear answering `nothing was pending under the key(s) this project reads (ac694bb5abad)`; both were true, about different files, and 138 records sat unfiled under nine keys while the same five findings came back at every review. Writing the command at render time leaves ONE derivation of the key instead of two that have to stay in step (L70, L285), which is the same drift this design already fixed once on the writing side. **That line also carries a STAMP of which records the render read** (claude-config#381), and a clear given one files only those: in an Ovation session on 2026-09-14 a review showed 4 findings, three more agents finished while its picker was open, and the clear filed 179 records including theirs, unread, because the line named files and a file keeps receiving records for as long as a picker is open. Rename then drain only protects the instant of the clear. The stamp is a digest of each record's canonical JSON (with `seen_by` left out) per key, not an offset, because `file-errors` rewrites the file straight after every render, a clear rewrites other sessions' records, and compaction rewrites the lot. It is written by the same read that produced the findings, lives beside the findings file named per session, and is moved into place only when the clear line is written. Records that arrived later go back pending and UNMARKED whoever owns them, and the clear says how many. A stamp that is named and cannot be read is a refusal that files nothing, never a fallback to filing the whole key, and a render that could not place its stamp writes no clear line at all, saying the findings come back next time instead. A clear with no stamp (a hand run one, or a line from before #381) still files everything of the session's under the keys. A clear that matches nothing now also says how many pending records the spool still holds under other keys, so the next mismatch is loud rather than silent. **A clear files only the CALLING SESSION's records** (claude-config#222): every record carries the session that produced it, and the project keying cannot tell two sessions apart, so whichever session's Stop hook fired first used to be handed every session's findings and file them before the others had ever seen them (measured in one PostRoll session on 2026-08-29, four consecutive reviews each handed the same 25 findings about work that session had not touched, copied aside by hand every time). A record naming no session at all is still filed by whoever clears first, because nothing can ever claim it. A finding from another session is still SHOWN, marked as one, since the reviewing session has no context for judging it and would either file it badly or drop it. It is shown ONCE (claude-config#322), and ownership EXPIRES (claude-config#326): a record whose session has not settled it within a week is treated exactly like one naming no session at all, shown to whoever is reviewing and filed by whoever clears, because a session that has ended never runs another review and #322 would otherwise have left those records visible to nobody and fileable by nobody. Filing them away unread instead would empty the spool while losing the finding, which is the worse of the two. a clear stamps the records it had to leave with the session it left them for, and the render skips a record this reader has already been stamped on, so an unsettleable finding stops arriving at every review while staying pending, unchanged, for the session that owns it. Two rules were colliding, that a clear files only its own session's records and that a review shows another session's so they are not dropped, and together they handed one session findings it could never settle, at every review, for as long as the owning session did not run its own (and one that has ended never will). The clear now also says how many it left and why, because "nothing was pending under this key" and "everything under this key is somebody else's" had the same words and the advice given for the second was to run the line the reader had just run. That `clear` SAYS what it did (claude-config#260): how many records it filed, out of which pending file, into which archive, or that nothing was pending under any key this project reads. Exiting 0 in silence made "it filed 49 records" and "it matched nothing" the same event, and when the same findings came back at the next review there was no way to tell a clear that had missed them from a harvest that had written them again. The rendered findings list carries a matching `SPOOL SOURCE:` line naming the files it was built from, so the two can be compared. A failure NOBODY CAN ACT ON (the nested subagent case below) is held back from every review and reported as a weekly count instead, because a notice carrying no action, delivered every turn, is what teaches a person to skip the whole review; held back is not discarded, and those records stay in the spool until that count actually goes out. A HARVEST FAILED record is the single exception, and it has to be: there is no action a person can take on one, a spool holding nothing else produces no picker, and nothing else ever runs `clear`, so before this it was re-attached to every review for that project until somebody emptied the spool by hand (measured 2026-08-18, one still being reported an hour later). A review that ACTUALLY CARRIED the spool text files the failures it carried, through `issue-spool.sh file-errors`, so being told once is the end of it; a review that could not build its pointer carries nothing and settles nothing. **Neither Stop hook holds its own instruction any more** (claude-config#243): a hook's `reason` is fed to Claude AND printed to Dan verbatim, so the issue review's instruction lives in `hooks/review/issue-review.md` (under 3,000 characters since 2026-10-15, its reasons in `issue-review-notes.md` beside it, and sent as a short repeat pointer once a session has read it), the reflection's in `hooks/review/session-reflection.md`, and the spooled findings go to a file under `$TMPDIR` rather than into the message. Each hook names its instruction by a path it resolves from its OWN location at run time, never a hardcoded one, so the same file is correct on both Macs with nothing to configure; a missing instruction file is reported as missing rather than skipped. What stays in the reason is anything the hook SETTLES by having reported it, which is the failure counts and the periodic held-back count, because a report whose only copy sits in a file nobody opened would be filed away unseen. Findings, unreadable records and everything else are untouched. Filing RENAMES the pending file and then drains the copy, rather than copying and truncating, because those are two steps with no lock and anything a finishing agent appends between them is destroyed; that is the one moment worth understanding, and the test for it drives a named seam (`CLAUDE_ISSUE_SPOOL_MIDCLEAR`) rather than racing real processes, which proved nothing because the window happened not to open. Only a real FINDING beats the review's cooldown, never a failure: repeated failures are deduplicated by reason and counted, and a recurring one (a subagent kind that leaves no transcript on disk fires about once a minute here) would otherwise keep the spool permanently non-empty and fire the review on every single turn. The harvest prompt deliberately covers agents whose JOB is finding problems: excluding those as "the task it was sent to do" harvested an agent that reported seventeen concrete defects as having found nothing. And `subagent-digest.py` answers with EXIT CODES (2 unreadable, 1 read fine but the agent said nothing, 0 a digest), because it prints nothing in both of the first two cases and a caller reading only its output files a corrupt transcript as a reassuring "found nothing". The digest also caps the TASK it shows the model, at 6000 characters (the 90th percentile of 508 real briefs measured 2026-10-06), and a trimmed task ends in a line beginning `[task trimmed by the digest` that the harvest prompt names and tells the model is not a finding (claude-config#860): a cap with no marker made a complete brief read as one cut off mid sentence, and it was filed as such three times in one day. **An agent can record a finding DIRECTLY, and for some agents it is the only way**: `bash ~/.claude/hooks/lib/issue-spool.sh note . "<the finding>" "<who is reporting>"`. The directory is a literal dot, never `"$PWD"` (claude-config#1342): Claude Code refuses a command from an agent isolated in a worktree that hands a script a runtime value, saying it "runs bash inside a construct too complex to verify", so the `"$PWD"` form this used to document could never run for exactly the agents it was written for, while the same call with a literal argument runs. `note` makes the directory absolute before recording it, because a bare dot stored as a record's `cwd` would be resolved later against whichever directory the reader stands in. The key is unaffected: it comes from the session's transcript, found through `CLAUDE_CODE_SESSION_ID`, which an agent shares with the session that dispatched it, and failing that from git's common dir, which takes a worktree to its main checkout, so the note lands where that session's review reads either way. It costs no model call, it does not depend on a transcript existing afterwards, and it lands in the same spool the review reads, so it is worth telling every agent you dispatch to use it. **A NESTED subagent cannot be harvested at all**, and that is not a defect to chase: an agent spawned by another agent fires SubagentStop with an `agent_transcript_path` that is never written, anywhere (measured 2026-08-16, 78 of them from three agent worktrees, none of the files present minutes later, and no nested transcript written under `~/.claude/projects` at all). So a batch of agents that each spawn their own helpers reports one deduplicated HARVEST FAILED line naming the count, which is honest and cheap: the refusal happens before the model is ever called, so those cost nothing. What is genuinely lost is whatever the nested helpers noticed. Turn the whole thing off for one run with `CLAUDE_ISSUE_HARVEST_OFF=1`, and give the model call a different deadline with `CLAUDE_ISSUE_HARVEST_TIMEOUT` (default 150 seconds, deliberately under the hook's own 180 second kill, because a killed hook writes no record at all and absence of a record is the one state this design cannot represent). Tests: `bash ~/.claude/hooks/run-all-tests.sh`.

**A clear that cannot do its work says so, and the seen marks survive it** (claude-config#1011). In a Slate session on 2026-10-09 the same two findings from another session came back at three reviews in a row; each time the clear line was run verbatim, printed nothing, and the spool was unchanged. Reproduced: when the clear cannot move a pending file aside (the spool directory cannot be written from where the line runs), the rename failed with its error discarded, and the summary only spoke for runs that had not failed, so a run that failed and filed nothing said nothing (the reproduction exits 1; the report said 0, and no branch of the clear is silent with 0). Now every exit speaks: a key whose file could not be moved names the file and the operating system's reason; a file another clear took in the instant before has its own sentence (exit 2 from the key, not a failure of the run, seam `CLAUDE_ISSUE_SPOOL_PRERENAME`); a split by session that cannot run files NOTHING, stamp or no stamp, where it used to fall back to filing every session's records; records the review read under a key this clear never reached (a directory retyped differently) are named; and a failed run ends with a sentence saying it did not finish. The other session's records a review was shown are marked seen in a SEEN LEDGER beside the stamp (`<stamp minus .manifest>.seen`, one derivation, `issue-spool.sh seen-ledger`) whenever the spool itself cannot be rewritten, because the mark has to be kept by a different write from the one that failed (L561); the render reads it, the same `seen_here` predicate now also decides `has-findings`, so a finding this reader will never be shown again no longer makes the review fire at every turn with nothing in it, and the render and the clear share one `unclaimed`, which they used to parse timestamps for differently. The ledger adds only marks it does not already hold, so a clear retried at every review does not grow it. And the `SPOOL SOURCE:` line counts only the records this reader is shown or can file, never other sessions' records already shown here: counted as raw lines, two reviews in a row both said "(57 records)" after a clear had really filed 42, which read as the clear not draining.

**The review's per session files are removed once spent, and a path outside ASCII survives** (claude-config#1019, #1020). Each render that shows findings leaves a stamp per session (`claude-issue-findings-<hash>.<session>.manifest`), a clear that could not rewrite the spool leaves a seen ledger beside it, and nothing removed either (26 stamps for one Slate project on 2026-10-09). Every render that shows findings now runs `issue-spool.sh sweep-stamps`, which removes, across every project, the review's stamps, ledgers and findings files untouched for longer than the ownership window (`CLAUDE_ISSUE_SPOOL_CLAIM_AFTER`, the same constant `unclaimed` reads): a mark in a ledger that old is for a record anybody may now claim, so `seen_here` no longer reads it, and a stamp that old belongs to a superseded render whose clear line would only be refused. It says how many it removed in the findings file, above the clear line so the file still ends with it, and names any file it could not remove. On this Mac macOS's own temp cleaner had already removed every such file older than about three and a half days (522 measured on 2026-10-12, none older), so the sweep is mostly the bound for a machine where that cleaner does not run; most of the pile was the suites, which now point `TMPDIR` at their own directory (257 of those 522 were the review suite's `.transcript.manifest` files). That same cleaner was a fault for the seen ledger, whose marks must last the week of the ownership window: once it removed a ledger, the finding it hid came back. The clear still WRITES its ledger in the temp directory, because the ledger exists for the clear that cannot write the spool and so cannot live under the spool's root (L561); but every working turn's review, which runs as a hook and can write the spool, copies every temp ledger (every project's and session's) into a kept copy of the same name under `<spool root>/seen/` (`issue-spool.sh keep-ledgers`, path from `kept-ledger <stamp>`, honouring `CLAUDE_ISSUE_SPOOL_DIR`), and the render and `has-findings` read both copies. It copies rather than moves, so a mark a clear appends meanwhile is taken next time; a kept ledger is rewritten only when it gains a mark, so the sweep judges it by the age of its newest mark; and a ledger that cannot be kept is named in the review's reason, whether or not there are findings, since a review with none writes no findings file. Ledgers written before this shipped sit at the same temp path, so they are read and kept like any other. The per session stamp stays in the temp directory: it only has to live from a render to the clear its line names, and a clear whose stamp has gone refuses and files nothing, saying so. The clear line is no longer written with `printf %q`, which under the bash macOS ships (3.2) wrote the curly apostrophe in the work MacBook's `Documents - Dan<U+2019>s MacBook Pro` as a raw byte plus octal escapes, so a reader saw a replacement character and a retyped line read different keys: each argument is left bare when it holds only characters no shell treats specially, and single quoted otherwise, keeping every byte. And a pending file is attributed by its records' `cwd` read with a JSON parser rather than sed, since the writers store that path as JSON and sed handed on the escape for a character outside ASCII undecoded, hashing a directory that does not exist.

**An agent that stopped only to WAIT is not harvested until its final stop** (claude-config#898). SubagentStop fires on every stop, including one where the agent waits on its own background work (a test run, a merge helper) and resumes when it reports; harvested then, the transcript reads as finished and the model files findings like "the merge was not completed" about an agent that merged minutes later (five about one agent on 2026-10-07). The payload's `background_tasks` is the whole SESSION's in flight work, not the agent's (Claude Code 2.1.293 builds it from the parent's task registry, so it lists the agent itself and every sibling), so an entry counts as the agent's own only when the agent's own transcript shows it LAUNCHED: the id follows a launch receipt (`with ID: `, `(ID: `, `(task `, `agentId: `) near the start of the result of the agent's own Bash, Monitor or Agent call, and a Bash result has to open with that receipt. Matching any mention was tried first and, on a real transcript, deferred the harvest for a sibling's work because a sibling's id appeared in an `ls` of the subagents directory. Anything the check cannot read (no field, not a list, an unreadable transcript, receipts worded differently by a later Claude Code) harvests exactly as before, because a skipped harvest leaves no record (L98). **A deferral is never a permanent skip**: losing an agent's findings for good is worse than the false findings the deferral removes. Each deferral is a PENDING HARVEST, one file per agent in `harvest-pending/` beside the spool, holding the payload to harvest it from, its deferral count and when it was first deferred. It is harvested anyway on the agent's next stop with no live work of its own, on the stop that would be its third deferral, or on a stop two hours after its first. An agent that never stops again, typically one that ended while its own Monitor still ran, is swept by any later harvest, from any session, once its record is overdue: the sweep claims the file by renaming it and harvests it in a background process of its own, removing the claim only once that harvest has run, and a claim whose harvest died is claimed again after 15 minutes. The file is cleared only once a harvest has actually written a record to the spool, so a harvest killed at the hook's limit, or one whose record could not be written, leaves it for a later sweep. A sweep and a late final stop of the same agent can both harvest it, which is the safe duplicate. The clock (`CLAUDE_ISSUE_HARVEST_NOW`) and the limits (`CLAUDE_ISSUE_HARVEST_MAX_DEFERRALS`, `CLAUDE_ISSUE_HARVEST_MAX_DEFER_SECONDS`) are seams, so the suite sets time rather than waiting for it. Every deferral, forced harvest and sweep writes a line to `harvest-deferred.log`, capped at 5000 lines like the archive. A transcript line that is valid JSON but not an object is skipped, by this check and by `subagent-digest.py` alike, and the digest reads a message, content or tool input of another shape as empty: before, one such line made the digest crash with exit 1, which the harvest reads as the agent saying nothing.

**A report handed back through the SubagentHandback tool is what the agent said** (claude-config#1232). An agent that ends by calling that tool writes its report as the tool's input, `{"message": <the report>}`, not as assistant text, so a digest reading only text blocks harvested such an agent as having said nothing: a `none` record, no model call, and every side finding in the report lost. Measured 2026-10-16 over the 229 real subagent transcripts on this Mac holding 286 such calls, every one a `tool_use` block of the same shape; 8 of those transcripts held no other words at all and went from exit 1 to a digest, and in the rest the report, usually the most finding dense part, now comes through at the end of what the agent said, which is the part trimming keeps. Only that tool is read this way: another tool's input that happens to carry a `message` field (a message to a sibling) is an action and stays out, and a handback whose message is not a non empty string is skipped like any other odd shape.

**A session that has ENDED releases its findings within hours, not a week** (claude-config#1291). The week of ownership (#326) was right while the owning session might still review, but one that has ended never will, so its findings sat unjudged for the whole week, shown once to each other session marked as another's to leave alone, then arrived at once, many out of date. Measured on Bidspoke on 2026-10-17: 135 of 233 pending records belonged to a session whose transcript had not been written for 16 hours. Now the one `unclaimed` predicate in `ISSUE_SPOOL_SEEN_PY`, which the render, `has-findings`, `seen_here` and the clear's split all read, also releases a record whose session has ended (`release_reason` says which: `ended` or `expired`). A session has ended when a `SessionEnd` hook (`hooks/issue-spool-session-end.sh`, registered in `settings.hooks.json`) stamped it, as one empty file `<spool root>/ended/<session id>` written by `issue-spool.sh mark-ended`, and it has written nothing more than a minute after the stamp (so a resumed session is owned again); or when its transcript, and every subagent transcript under `<session>/subagents/`, found under `CLAUDE_TRANSCRIPT_ROOT` (default `~/.claude/projects`), has been idle past `CLAUDE_ISSUE_SPOOL_ENDED_IDLE` (default 4 hours), which covers a session that ended without the hook (a crash, a closed terminal). A session with no stamp and no transcript to read stays owned, since absence is not evidence it ended (L50), and the week stays as the backstop for it. The render marks a released finding as from a session that has ended, the reader's to judge and file, with its age on the line as every finding has. `mark-ended` takes a plain name only (the id becomes a file name), refuses the real spool under a test run as `append` does, and removes stamps older than the ownership window as it writes. The suite points `CLAUDE_TRANSCRIPT_ROOT` at its own folder, so no verdict depends on which sessions the Mac running it has.
