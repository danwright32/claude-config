# Subagent issue harvest: how it works and what not to break

Moved out of `~/.claude/CLAUDE.md` on 2026-09-17, word for word, because it was 11,800 characters
loaded into every session and is only needed when changing the harvest, the spool or the issue
review. CLAUDE.md keeps a short pointer here. Read this whole file before editing
`hooks/subagent-issue-harvest.sh`, `hooks/lib/issue-spool.sh`, `subagent-digest.py` or the review hooks.

**Subagent findings are harvested, not remembered.** The issue review above is a `Stop` hook: it fires when the MAIN session stops, on a 30 minute per project cooldown, reading the main transcript. None of that reaches a subagent, so before 2026-08-16 every observation an agent made while working died with it, and a batch of parallel agents got at most one review between them. `hooks/subagent-issue-harvest.sh` is a `SubagentStop` hook that reads the finishing agent's own transcript and spools anything it noticed but was not sent to fix. It asks the agent for nothing, because an instruction to report findings is a rule living only in a prompt (L27) and reaches nothing in exactly the batches where it matters. It runs `async`, so it never delays an agent, and it runs a cheap headless Haiku pass, so it costs one small call per agent. Five things to know before changing it. **The transcript to read is `agent_transcript_path`, never `transcript_path`.** A SubagentStop payload carries both, and `transcript_path` is the transcript of the session that SPAWNED the agent. The first version read that one, which does not fail: it harvests the parent conversation and spools findings that look entirely real, and it was caught only by reading the spool file by hand (2026-08-16, three records, every one of them about the parent session). There is deliberately NO fallback to `transcript_path` in any of the three ways it can arrive wrong (absent, equal to the parent, or naming a file that is not there); each is a loud error record instead, and each error names its own cause, because the same-file guard will otherwise answer for the missing-field guard and a reintroduced fallback passes the suite (seen to survive, then caught). The spool lives at `~/.claude-issue-spool/`, deliberately OUTSIDE `~/.claude`, because anything under `~/.claude` auto pushes to the other Mac within seconds and transcript derived notes are not config. Every record also carries the PROJECT key it belongs to, resolved when the record is written (claude-config#294), because attribution used to re-resolve a record's `cwd` later and an agent's cwd is routinely a git worktree that every AGENTS.md says to remove once its PR merges: once it is gone the resolution hashes a path that is not there and the record belongs to nobody. Measured 2026-09-03, 111 of 170 pending records were written from a worktree cwd, and one file held 106 findings nothing could reach. The stamp cannot help a record written before it shipped (L223), so a reader still resolves `cwd` too, and a worktree path also resolves through the checkout it belongs to. It is keyed on the directory of the PARENT SESSION's transcript, which both the harvest and the review derive from the same conversation, so the writer and the reader cannot compute different keys (L70); git's common dir is the fallback for a caller with no transcript (a direct `note`, a test), and a reader also consults that key so nothing spooled the old way is stranded. Keying each side on its own working directory is what let the two drift apart, and 47 findings sat unread for a week because of it. An agent that found NOTHING still leaves a record saying it looked, and an agent whose harvest FAILED leaves a differently worded one, because otherwise both read as a project with no findings (L98, L11). And reading the spool does not empty it: only a `clear` does, run after the picker is answered, so a review that is read and then interrupted leaves the findings behind for the next one. **The review WRITES that clear command into the findings file** (claude-config#287, claude-config#284), on a line reading `TO FILE THESE`, and that line is to be run exactly as it stands. It is not a convenience: a clear takes a directory AND the session transcript, and one given only a directory keys on the git common dir while the render keyed on the transcript's directory. The documented fixed form passed no transcript, so on 2026-09-03 a findings file naming `bfea61f932c1.jsonl (107 records)` was followed by a clear answering `nothing was pending under the key(s) this project reads (ac694bb5abad)`; both were true, about different files, and 138 records sat unfiled under nine keys while the same five findings came back at every review. Writing the command at render time leaves ONE derivation of the key instead of two that have to stay in step (L70, L285), which is the same drift this design already fixed once on the writing side. A clear that matches nothing now also says how many pending records the spool still holds under other keys, so the next mismatch is loud rather than silent. **A clear files only the CALLING SESSION's records** (claude-config#222): every record carries the session that produced it, and the project keying cannot tell two sessions apart, so whichever session's Stop hook fired first used to be handed every session's findings and file them before the others had ever seen them (measured in one PostRoll session on 2026-08-29, four consecutive reviews each handed the same 25 findings about work that session had not touched, copied aside by hand every time). A record naming no session at all is still filed by whoever clears first, because nothing can ever claim it. A finding from another session is still SHOWN, marked as one, since the reviewing session has no context for judging it and would either file it badly or drop it. It is shown ONCE (claude-config#322), and ownership EXPIRES (claude-config#326): a record whose session has not settled it within a week is treated exactly like one naming no session at all, shown to whoever is reviewing and filed by whoever clears, because a session that has ended never runs another review and #322 would otherwise have left those records visible to nobody and fileable by nobody. Filing them away unread instead would empty the spool while losing the finding, which is the worse of the two. a clear stamps the records it had to leave with the session it left them for, and the render skips a record this reader has already been stamped on, so an unsettleable finding stops arriving at every review while staying pending, unchanged, for the session that owns it. Two rules were colliding, that a clear files only its own session's records and that a review shows another session's so they are not dropped, and together they handed one session findings it could never settle, at every review, for as long as the owning session did not run its own (and one that has ended never will). The clear now also says how many it left and why, because "nothing was pending under this key" and "everything under this key is somebody else's" had the same words and the advice given for the second was to run the line the reader had just run. That `clear` SAYS what it did (claude-config#260): how many records it filed, out of which pending file, into which archive, or that nothing was pending under any key this project reads. Exiting 0 in silence made "it filed 49 records" and "it matched nothing" the same event, and when the same findings came back at the next review there was no way to tell a clear that had missed them from a harvest that had written them again. The rendered findings list carries a matching `SPOOL SOURCE:` line naming the files it was built from, so the two can be compared. A failure NOBODY CAN ACT ON (the nested subagent case below) is held back from every review and reported as a weekly count instead, because a notice carrying no action, delivered every turn, is what teaches a person to skip the whole review; held back is not discarded, and those records stay in the spool until that count actually goes out. A HARVEST FAILED record is the single exception, and it has to be: there is no action a person can take on one, a spool holding nothing else produces no picker, and nothing else ever runs `clear`, so before this it was re-attached to every review for that project until somebody emptied the spool by hand (measured 2026-08-18, one still being reported an hour later). A review that ACTUALLY CARRIED the spool text files the failures it carried, through `issue-spool.sh file-errors`, so being told once is the end of it; a review that could not build its pointer carries nothing and settles nothing. **Neither Stop hook holds its own instruction any more** (claude-config#243): a hook's `reason` is fed to Claude AND printed to Dan verbatim, so the issue review's 8,000 character instruction lives in `hooks/review/issue-review.md`, the reflection's in `hooks/review/session-reflection.md`, and the spooled findings go to a file under `$TMPDIR` rather than into the message. Each hook names its instruction by a path it resolves from its OWN location at run time, never a hardcoded one, so the same file is correct on both Macs with nothing to configure; a missing instruction file is reported as missing rather than skipped. What stays in the reason is anything the hook SETTLES by having reported it, which is the failure counts and the periodic held-back count, because a report whose only copy sits in a file nobody opened would be filed away unseen. Findings, unreadable records and everything else are untouched. Filing RENAMES the pending file and then drains the copy, rather than copying and truncating, because those are two steps with no lock and anything a finishing agent appends between them is destroyed; that is the one moment worth understanding, and the test for it drives a named seam (`CLAUDE_ISSUE_SPOOL_MIDCLEAR`) rather than racing real processes, which proved nothing because the window happened not to open. Only a real FINDING beats the review's cooldown, never a failure: repeated failures are deduplicated by reason and counted, and a recurring one (a subagent kind that leaves no transcript on disk fires about once a minute here) would otherwise keep the spool permanently non-empty and fire the review on every single turn. The harvest prompt deliberately covers agents whose JOB is finding problems: excluding those as "the task it was sent to do" harvested an agent that reported seventeen concrete defects as having found nothing. And `subagent-digest.py` answers with EXIT CODES (2 unreadable, 1 read fine but the agent said nothing, 0 a digest), because it prints nothing in both of the first two cases and a caller reading only its output files a corrupt transcript as a reassuring "found nothing". **An agent can record a finding DIRECTLY, and for some agents it is the only way**: `bash ~/.claude/hooks/lib/issue-spool.sh note "$PWD" "<the finding>" "<who is reporting>"`. It costs no model call, it does not depend on a transcript existing afterwards, and it lands in the same spool the review reads, so it is worth telling every agent you dispatch to use it. **A NESTED subagent cannot be harvested at all**, and that is not a defect to chase: an agent spawned by another agent fires SubagentStop with an `agent_transcript_path` that is never written, anywhere (measured 2026-08-16, 78 of them from three agent worktrees, none of the files present minutes later, and no nested transcript written under `~/.claude/projects` at all). So a batch of agents that each spawn their own helpers reports one deduplicated HARVEST FAILED line naming the count, which is honest and cheap: the refusal happens before the model is ever called, so those cost nothing. What is genuinely lost is whatever the nested helpers noticed. Turn the whole thing off for one run with `CLAUDE_ISSUE_HARVEST_OFF=1`, and give the model call a different deadline with `CLAUDE_ISSUE_HARVEST_TIMEOUT` (default 150 seconds, deliberately under the hook's own 180 second kill, because a killed hook writes no record at all and absence of a record is the one state this design cannot represent). Tests: `bash ~/.claude/hooks/run-all-tests.sh`.
