On approval, file with `gh issue create` in the CURRENT repository (do not hardcode a repo): a concise imperative title and a 2-4 sentence body covering the problem, why it matters, a rough direction, and relevant `path:line` refs. MILESTONE AND PRIORITY, BOTH REQUIRED: every issue carries a milestone and exactly one priority label, and one PreToolUse gate blocks a create that is missing any of them. Work BOTH out for every idea BEFORE showing the picker, and SHOW THEM IN THE PICKER so I can see what you chose and correct it before anything is filed: end each option description with all three in brackets, in this order, priority then categories then milestone, like `[p2, tech-debt, Queue windowing]` or `[p1, bug, Ungrouped]` or, for a milestone this review would open, `[p2, tech-debt, NEW Backlog grouping, moves #241 #242]`. MILESTONE: a milestone is an overarching FEATURE, and its issues are what has to be finished for that feature to ship. Do NOT reach for the catch-all first. The score RANKS that shortlist and rules on nothing: `CANDIDATE-COUNT` says how many were listed, never how many are related. READ THE TITLES and decide which are genuinely siblings, then use YOUR count for the 2 or more rule and for `--for-issues`. Word counting was wrong three times on the day it was written, always claiming a cluster that was not there, and each fix excluded the words that exposed it, so the next repo has its own generic words and the script cannot know them (claude-config#265). Promote a candidate only if you can say what it actually shares. It also prints DUPLICATE-RISK lines for open issues ANYWHERE in the repo, not just the pen, that overlap with the idea, each naming the milestone it already sits in, with a DUPLICATE-COUNT. CHECK THOSE BEFORE FILING: an idea that already exists must not be filed again, and on 2026-09-02 one was, because the helper only read the holding pen and the issue for the same work sat in a real milestone. A DUPLICATE-RISK is not a sibling and never counts toward the 2 or more rule; read it, and if it is genuinely the same work, drop the idea and say which issue already covers it instead of filing.
